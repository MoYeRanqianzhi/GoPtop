# 2026-09-19 聊天停靠栏三档布局（用户拍板：等宽 → 压缩 → 弹窗）

用户原话要点：聊天区在右侧时「最大宽度设置为跟棋盘区的宽度相同，左右两边大小相同，
视觉上更雅观」；放不下时「优先对聊天区进行压缩宽度，因为该软件本质上是下棋软件，
优先显示完整的棋盘内容更为重要」；「宽度足够小时…变为之前策略中显示不下时以弹窗
形式显示的这种情况」。

## 落地规则（三档，全部实测，不看视口断点）

1. **等宽档**：空间够 → 停靠栏宽度 = `.play-stack` 整组宽度（即棋盘那一列的宽度），
   左右两栏对称。
2. **压缩档**：放不下 → 先压缩停靠栏（棋盘半点不让）。
3. **弹窗档**：停靠栏压到 `CHAT_MIN_W = 240` 仍放不下 → 改弹窗形态（与窄屏同一策略）。

实现在 `frontend/src/App.tsx` 的 `measureChat()`：在 `--stack-max` 落定后量
`- 已占宽度(除停靠栏外所有 .game-layout 子项) - 间隙`，取
`min(stackW, avail)` 写 `--chat-w`，并 `setChatDocked(dockW >= CHAT_MIN_W)`。
停靠栏与弹窗**互斥渲染**（旧实现两份 DOM 并存），弹窗移出 `.game-layout`
（固定定位元素若留在里面会被宽度实测当成一个占位子项）。
**旧的 `@media (min-width: 1080px)` 断点全删**：视口宽度猜不出「整组被高度压窄」，
这正是用户说的「空间不足但较为充足」那一段被漏判的原因。

## 踩到的正反馈（第二次踩，务必记住）

只加停靠栏宽度计算还不够：修前在 650/600 两档实测到**棋盘被压小且回不来**。
链条是：停靠栏按旧宽度渲染 → 整行超出 → `.play-stack` 被 flex 压缩（`flex: 0 1 auto`）
→ 下一帧 `measureChat` 量到的就是**被压窄后的整组宽度**，于是把腾出来的空间
永久判给停靠栏 → 棋盘再也回不到原宽。
修法：`.play-stack` 改 `flex: 0 0 auto`（棋盘整组宽度是硬锚点，任何情况不许被压窄），
超额部分由停靠栏自己收敛，收敛不下去就退弹窗。

## 实测（本机 chromium，A/B 真实配对入局 + 真实点击开聊天）

| 视口宽 | 形态 | 整组 | 棋盘 | 停靠栏 |
|---|---|---|---|---|
| 1600–850 | 停靠栏（等宽） | 393 | 349 | 393 |
| 800 | 停靠栏（压缩） | 393 | 349 | 369 |
| 760 | 停靠栏（压缩） | 393 | 349 | 329 |
| 710 / 680 | 停靠栏（压缩） | 393 | 349 | 279 / 249 |
| ≤660 | 弹窗 | 393 | 349 | 0 |
| 393（Pixel 5） | 弹窗 | 355 | 303 | 0 |

棋盘宽度在所有档位恒定（349），即「棋盘完整优先」成立；各档无横向溢出。
桌面壳 1100×760：停靠栏 261 = 整组 261（等宽），棋盘 182 与关聊天时一致。
目视截图核对：等宽档左右两栏对称、压缩档聊天栏变窄而棋盘不动、弹窗档棋盘在弹窗后可见。

回归：`node scripts/e2e/run.js` 新增 13a–13g 七项（宽屏等宽 / 偏窄压缩 / 更窄弹窗 /
每档断言棋盘宽度不变 / 无横向溢出），基线 42 → **49/49 全绿**。

**Why:** 「停靠栏该多宽」是设计取舍（左右对称 vs 棋盘优先），用户给了明确优先级；
而实现上它天然是个「两个变量比大小」的判断，CSS 媒体查询表达不了（宽度锚点还依赖窗口高度），
只能实测。正反馈那条坑不改 `flex-shrink` 会稳定复现，下次动这块布局必然再撞。

**How to apply:** 改对局页布局后按上表三个宽度各看一次；**别再引入视口宽度断点**
判断聊天形态；`.play-stack` 的 `flex: 0 0 auto` 是红线，见
`.agents/docs/architecture.md` 自适应布局节与 `real-device-testing.md` §6。
