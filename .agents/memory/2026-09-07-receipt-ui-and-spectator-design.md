## 用户拍板的设计决策

1. **同浏览器双窗口（BroadcastChannel 对弈/观战）是极端情况，基本不需要考虑。**
   开发与测试的基准场景是跨设备 WebRTC 直连。不得再为同源双窗口场景做专门的 UI/流程优化。

2. **项目现状认知：之前的项目开发基本全是 bug，需要慢慢修复。**
   - 修复时以最小改动对准根因，不做顺手重构。
   - 此前开发完全无视了 CLAUDE.md 的记忆要求，项目里没有记忆——现已补齐（本文件与 TODO.md 即开始）。**今后每次拍板、每次修复根因都必须落记忆，不能只改代码。**

3. **回执 UI 三条硬性要求：**
   - ~~「输入回执」按钮**始终在页面上**（常驻可见，不只在 host 等待页出现）。~~
     **2026-09-07 晚推翻**：header 空间宝贵（手机端致命挤压），「输入回执」撤出顶部导航，唯一入口在等待页（commit 8e1524c）。常驻改为"粘贴解析能力任何页面可用"（parsePasted* 与域名无关），不要求按钮常驻。
   - 回执确认按钮文案**不得写「开局」**——回执不一定是加入对局，也可能是观战回执。
   - **回执的用途由回执链接自带的属性自动判断**：粘贴后前端解析属性自动识别是「加入对局回执」还是「观战回执」，然后自动建立对应的 P2P 连接。用户无需选择、无需手动区分。

3.5 **UI 冗余与手机端（2026-09-07 晚拍板，commit 8e1524c）：**
   - 大量解释性文字是冗余：pwd 说明、跨设备流程说明、直连约束说明等一律不展示，界面只留操作。
   - header 手机端三级降级：排列不下先隐「GOMOKU · 15×15」徽章，再隐 GoPtop 标题，最后把对局设置压成「类型」弹出按钮——最终顶部只剩「类型」「菜单」。
   - 「输入回执」不放顶部导航。
   - 「选项」入口统一改名「菜单」。

4. **观战拓扑：观战者只与邀请者（邀请者）之间建立 P2P 直连。**
   一名观战者一条独立连接，不观战者互联、不中继。邀请者向所有已建立的连接（选手 + 各观战者）广播对局消息。
